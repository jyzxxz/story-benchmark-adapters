# R5.3 Validation - Supersede Previous Active Release

## Scope

- Extended the atomic publish transaction to lock and validate the current
  ProjectPublication active Release.
- Rejected a damaged active pointer with `release.active_invalid` and an
  unchanged reviewed fingerprint with `release.no_changes`.
- Created the next immutable Release version before marking the previous active
  Release `superseded` and moving the ProjectPublication pointer.
- Kept `withdrawn_at` null for superseded Releases; supersede and withdrawal
  remain distinct terminal transitions.
- Preserved idempotent replay: replaying an older successful key returns that
  original (now superseded) Release without moving the current pointer.
- Kept the Release insert, old-status transition, and pointer move in the same
  savepoint so an exception restores all three.

## Coupling Audit

- **Publication lock:** version allocation, status transition, and pointer move
  remain serialized per project.
- **R5.1 fingerprint:** supersede occurs only after a changed, ready snapshot has
  passed the same double-read source validation as first publication.
- **Release immutability:** manifest, fingerprint, notes, and publication times
  of the previous Release are unchanged; only its lifecycle status transitions.
- **Public reads:** R5.3 does not expose superseded Releases. R5.4 enforces the
  active-pointer rule for all public endpoints.
- **Legacy fields:** no Project visibility/draft field or legacy content-head
  publication pointer participates in supersede.
