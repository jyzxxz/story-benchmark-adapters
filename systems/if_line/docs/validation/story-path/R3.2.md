# R3.2 Validation - Candidate Set Head Review Flow

## Scope

- Added CandidateSet review queries scoped by exact
  `(story_path_id, checkpoint_node_id)` identity. Revision history is returned
  newest first; candidates are returned in the immutable manifest order.
- Made CandidateSetRevision `candidates_json` and `content_hash` the
  authoritative review payload. Candidate text is not read from mutable preview
  StoryNodes, and every query validates the payload hash and linked candidate
  rows.
- Added discoverable empty CandidateSet Heads. A Head starts with
  `revision_id = null` and `lock_version = 1` before the first review choice.
- Added optimistic CandidateSet Head activation with the common `If-Match`
  compare-and-swap behavior. First selection increments the version, matching
  re-selection is a no-op, and stale selection returns the current Head in
  `409 head.version_conflict` details.
- Required a selectable CandidateSet to belong to the exact path checkpoint,
  retain a valid StateSnapshot and payload, and reference the ChapterRevision
  currently selected on that StoryPath. Sets from a replaced Chapter Head stay
  visible in history but cannot be activated.
- Kept activation review-only: it does not mutate CandidateSetRevision,
  BranchCandidate, Chapter Head, BranchEdge, or StoryPath.
- Added migration `0029_nullable_candidate_set_head`. Its downgrade removes
  only empty Heads before restoring the old non-null constraint.
- Added target response schemas for CandidateSetRevision and ordered
  BranchCandidate review data.

## Coupling Audit

- **Generation:** R3.1 still creates review-only CandidateSetRevisions and
  never moves a Head. Its recovery path now reuses the same payload validator
  as review queries, preventing validation drift.
- **Chapter:** activation verifies the exact ChapterRevision selected by the
  path; no `chapter_index` lookup participates in ownership or authorization.
- **Head concurrency:** the checkpoint row serializes first-Head creation, and
  the composite Head row performs SQL compare-and-swap on `lock_version`.
- **Candidate data:** ordered text and state come from CandidateSetRevision;
  BranchCandidate rows are referential anchors and must match that payload.
- **Promotion:** selection does not create BranchEdges, StateSnapshots, or
  StoryPaths. R3.3 consumes only a candidate from the active reviewed Head and
  performs those writes in one transaction.
- **Publication:** CandidateSet Head is authoring state only. Public reading
  remains bound to an immutable Release manifest.
- **HTTP:** services and response schemas are ready; route registration and
  owner authorization remain R6.2.
- **Migration:** nullable Heads are additive and do not choose a revision or
  backfill legacy candidate relationships. That remains R7.2.
