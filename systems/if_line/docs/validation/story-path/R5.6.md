# R5.6 Validation - Atomic Publication Lifecycle

## Scope

- Added end-to-end service tests for continued authoring while an immutable
  Release remains active and publicly readable.
- Verified that creating an unselected ChapterRevision does not change the
  authoring fingerprint or create a StoryPath, while selecting it changes only
  the owner projection and leaves the active public manifest and VNGraph frozen.
- Simulated two independent stale clients that captured the same fingerprint
  before first publish and before a superseding publish.
- Covered both idempotent same-key replay and different-key no-change conflict;
  exactly one Release is created for each authoring fingerprint.
- Injected failures after tentative first activation and after tentative
  supersede, including explicit flushes, and verified complete savepoint
  rollback of Release rows, status, pointer, timestamp, lock version, and
  idempotency state.
- Verified that retrying the same key after rollback succeeds and that the old
  Release remains publicly readable until a replacement transaction commits.
- Added a PostgreSQL-only two-thread test for real ProjectPublication row-lock
  serialization. It is skipped on SQLite rather than claiming SQLite
  `FOR UPDATE` behavior as production concurrency coverage.

No production code changed in R5.6.

## Lifecycle Assertions

- **Continued editing:** unselected attempts are not unpublished changes;
  selecting a new Chapter Head is `changes_pending` while public readers still
  receive the old chapter and graph.
- **First-publish race:** two clients with the same pre-publish fingerprint
  produce one version-1 Release and one active pointer. A repeated key replays;
  a different key receives `release.no_changes`.
- **Supersede race:** two clients with the same changed fingerprint produce one
  version-2 Release, one superseded version-1 Release, and lock version 3.
- **First activation failure:** no ProjectPublication, Release, pointer,
  timestamp, lock increment, or idempotency residue survives.
- **Supersede failure:** version 1 stays published and active, no version 2 row
  survives, and public reads remain available.
- **Retry:** the exact failed idempotency key can subsequently create the
  intended Release because the failed transaction left no key reservation.

## Coupling Audit

- **Revision versus branch:** an additional ChapterRevision remains an attempt;
  no StoryPath is created until explicit branch promotion.
- **Projection:** selected authoring changes alter only the computed owner state
  until a successful publish moves the pointer.
- **Public reads and media:** all continue through the previous active Release
  during editing and failed replacement attempts.
- **Database locking:** portable tests verify serialized outcomes using separate
  sessions; the conditional PostgreSQL test verifies simultaneous row-lock
  behavior where `SELECT FOR UPDATE` is meaningful.
- **Atomicity:** failure injection occurs after rows and pointer updates have
  flushed, proving rollback rather than merely proving early validation.
