# R6.1 Validation - Path-Based Authoring API

## Scope

- Added separate Project, Bible, StoryPath, Outline, and Chapter routers under
  `/api` with the replacement paths frozen in the StoryPath OpenAPI contract.
- Project creation now atomically creates one root StoryPath, an empty
  ProjectContentHead, and an empty StoryPathOutlineHead.
- Project reads are owner-only and return computed authoring/publication
  projections. Legacy Project status, visibility, draft, and publication fields
  are not exposed as authoring state.
- Project list filtering uses `unpublished`, `published`, and
  `changes_pending`; project and artifact metrics use stable UUID keys.
- Bible, Outline, and Chapter generation endpoints enqueue durable Tasks and
  return TaskAccepted. They never invoke a provider in the request process and
  never move a Head.
- Manual Bible, Outline, and Chapter writes create unselected immutable
  revisions. Every Head update requires `If-Match`, returns an ETag, and uses
  the R2.5 compare-and-swap services.
- Outline generation accepts every explicit chapter count from 1 through 500.
  Outline activation reconciles stable PathChapter IDs without replacing IDs
  retained by a later OutlineRevision.
- Chapter generation and batches accept PathChapter UUIDs and freeze the exact
  StoryPath, predecessor chain, selected Bible, selected Outline, and state.
- Candidate promotion through `POST /projects/{id}/story-paths` delegates to
  the R3.3 transaction service and cannot construct an arbitrary fork.
- UUID ownership is resolved back to the owning Project and cross-owner reads
  return 404 without leaking resource existence.

## Router Cutover

The legacy Project router and the replacement Project router both own
`GET /api/projects/{project_id}`, so they cannot coexist in one FastAPI route
table without making runtime dispatch differ from OpenAPI. R6.1 switches the
main application registration to the replacement Project router and leaves the
legacy module file present for deletion in R8.1. Other non-conflicting legacy
authoring routers remain registered until their replacement groups and the
frontend are complete.

R6.1 is an intermediate source-control checkpoint, not an independently
deployable release. Backend, frontend, migration, and legacy-route removal are
deployed once as required by the frozen cutover policy.

## Contract Clarification

`PathChapterCreate.title` was removed from the frozen OpenAPI schema during
implementation review. StoryPathChapter has no mutable title field; chapter
titles are immutable OutlineChapter payload. Accepting the field would silently
discard author data. The endpoint now accepts only `after_path_chapter_id`, and
unknown `title` input returns 422.

## Coupling Audit

- **Project projection:** owner responses call the single R5.5 projection and
  the R5.1 readiness calculator; routers do not recreate lifecycle logic.
- **Branching:** only candidate promotion calls the R3.3 service. The old
  project-level candidate-generation route is not an input to StoryPath reads,
  Outline generation, or Chapter generation.
- **Outline:** both generation and activation call R2.3 services. The HTTP body
  does not infer chapter count from pace or fixed presets.
- **Chapter:** generation, manual edits, and batches resolve PathChapter UUIDs
  and call R2.4 services; presentation indexes are not resource selectors.
- **Heads:** Bible, Outline, and Chapter selection exclusively uses R2.5 CAS
  services and independent lock versions.
- **Tasks:** every generation request persists Task, usage reservation, Task
  event, and outbox event in the request transaction.
- **OpenAPI:** all 19 grouped R6.1 paths expose the exact method sets in the
  frozen contract, and the complete generated FastAPI snapshot is current.
