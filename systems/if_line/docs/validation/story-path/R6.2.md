# R6.2 Validation - Branch, Graph, and Publication API

## Scope

- Registered the 27 frozen Candidate, Script, resource, VNGraph, Release, and
  public method/path pairs directly below `/api`.
- Candidate generation freezes the exact StoryPath, checkpoint,
  ChapterRevision, StateSnapshot, and idempotency identity. Candidate review
  uses the R3 Head CAS and promotion delegates to the R3 transactional
  Candidate-to-StoryPath service.
- Script generation, history, and Head selection are keyed by an exact
  ChapterRevision UUID. Optional author instructions are normalized, persisted
  in the Task parameters, and included in the annotation request.
- Resource planning and rendering are keyed by ChapterScriptRevision UUID.
  Caller idempotency is propagated to the durable batch Task. Manual resource
  binding requires `If-Match`, increments a per-Slot lock version, and preserves
  the existing automatic VNGraph queue behavior when all required Slots bind.
- VNGraph compilation, history, and Head selection are keyed by an exact
  ChapterScriptRevision UUID. Standalone reads resolve an exact VNGraphRevision
  UUID and hide cross-owner existence.
- Owner publication routes delegate to the R5 atomic publish/unpublish
  services. Public catalog, project, manifest, chapter manifest, and graph
  reads delegate to the active-Release-only public service and never read live
  authoring tables for content.

## Router Cutover

The legacy Release router and replacement router own the same owner and public
GET paths. Registering both would make FastAPI dispatch differ from generated
OpenAPI, so R6.2 removes the legacy Release router registration and registers
the replacement Release/Public router. The legacy module remains in the tree
for R8.1 deletion.

Legacy Candidate, Script, and VNGraph routes with different chapter-index URLs
remain registered during the R6 intermediate checkpoint. They do not own any
replacement method/path pair and are removed together in R8.1 after the
frontend and historical data have switched. R6.2 is not deployed separately;
the backend, frontend, migrations, and route deletion remain one release unit.

## Resource Slot Concurrency Migration

The frozen ResourceSlot contract requires `If-Match` and `lock_version`, while
the pre-R6.2 persistence model had no Slot lock. Migration
`0035_script_resource_slot_lock` adds a positive, non-null lock with a default
of 1 and supports SQLite and PostgreSQL.

Migration behavior is explicitly tested against a synthetic database stamped
at 0034 with a real historical Slot row and no lock column. Upgrade backfills
the row to 1, rejects lock value 0, downgrade preserves the row, and a second
upgrade restores the lock. The migration also tolerates a complete column and
constraint already present because migration 0020 historically creates tables
from current ORM metadata on a fresh database.

## Coupling Audit

- **Candidates:** routers perform ownership resolution and delegate generation,
  Head review, listing, and promotion to the R3 services. Candidate revisions
  remain retries/reviews; only promotion creates a StoryPath branch.
- **Scripts:** routes key every operation by ChapterRevision or
  ChapterScriptRevision UUID and delegate immutable generation and Head CAS to
  R4 services. Instructions are part of the frozen Task input.
- **Resources:** the existing AssetPlan/Task fanout remains authoritative. The
  route contributes caller idempotency and Slot optimistic concurrency without
  introducing a second asset pipeline.
- **VNGraph:** compile input is the immutable ScriptRevision plus frozen Asset
  and VoiceLine versions from R4. No route assembles by project and display
  index.
- **Publication:** `/publish` and `/unpublish` are thin adapters over the R5
  atomic transaction and ProjectPublication CAS. Public routes exclusively use
  active Release snapshots.
- **Tasks:** all generation, rendering, and compilation requests remain durable
  Task transactions and preserve replay/conflict semantics.
