# R7.4 Validation - StoryPath And Release Backfill Audit

## Scope

- Added `backend/scripts/verify_story_path_release_backfill.py` as a read-only,
  two-stage deployment audit.
- Captures a pre-backfill baseline at Alembic revision
  `0035_script_resource_slot_lock`.
- Verifies the migrated database at
  `0038_backfill_project_publications`.
- Added an end-to-end test that runs the CLI across the real Alembic chain and
  proves damaged Heads, manifests, public access, and snapshots fail closed.

## Run Order

Authoring and publication writes must remain paused between capture and
verification. Run the following against the same database:

```bash
cd backend

venv/bin/python -m alembic -c alembic.ini upgrade 0035_script_resource_slot_lock
venv/bin/python scripts/verify_story_path_release_backfill.py capture \
  --output /secure-backup/story-path-backfill-before.json

venv/bin/python -m alembic -c alembic.ini upgrade 0038_backfill_project_publications
venv/bin/python scripts/verify_story_path_release_backfill.py verify \
  --snapshot /secure-backup/story-path-backfill-before.json
```

Both commands use the configured `DATABASE_URL`. Capture requires exactly
`0035`; verification requires exactly `0038`. A malformed, incomplete, or
modified snapshot is rejected before post-migration checks run. Exit status 0
means every check passed; status 1 means deployment must stop.

The snapshot contains only table counts and SHA-256 row fingerprints. It does
not contain story text, manifest payloads, user details, or plaintext row IDs.
Its checksum detects accidental or unreviewed modification. The snapshot still
belongs with the database backup and must be stored under the same access
controls.

## Count And Preservation Checks

The verifier requires exact before/after counts for immutable source rows,
including Projects, legacy Heads, revisions, candidates, Releases, and reading
sessions. Tables legitimately populated by R7.1-R7.3 are grow-only, including
StoryPaths, ChapterSlots, PathChapters, StateSnapshots, artifact Heads, and
ProjectPublications.

Row fingerprints additionally prove exact preservation of:

- legacy Project publication fields;
- ProjectContentHead and ChapterHead rows;
- every immutable Release manifest and timestamp, excluding only its mutable
  lifecycle status; and
- every Script and VNGraph Head that existed before the backfill.

## Relation And Head Checks

The post-migration audit rejects:

- projects without exactly one root StoryPath or root Outline Head;
- incomplete or cross-project ChapterRevision/ChapterSlot/path bindings;
- broken predecessor chains;
- root Chapter Heads whose selected Revision or lock differs from the legacy
  ChapterHead;
- Outline rows outside their exact PathChapter and selected Outline Heads that
  differ from the legacy UUID;
- missing Script/VNGraph Heads or selected Heads tied to another immutable
  source Revision; and
- candidates or selected CandidateSet Heads tied to another checkpoint/path.

`chapter_index` appears only in this deployment audit to compare retained
legacy Heads and frozen display metadata with their migrated UUID relations.
It is not imported by the application and does not participate in runtime
identity resolution.

## Manifest And Public Readability

Every Release manifest is parsed and rehashed with the application's canonical
hash function. Immutable Release fingerprints must match the baseline exactly.
Every active ProjectPublication must point to one non-withdrawn `published`
Release, and no other Release may remain `published`.

The verifier then calls the production public Release service for every
Release. Every active Release must resolve successfully; every superseded,
withdrawn, or otherwise non-active Release must resolve as not found. This
checks actual public-read behavior rather than only duplicating its SQL.
