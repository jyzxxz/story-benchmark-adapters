# R6.4 Validation - StoryPath Authoring Workflow

## Scope

- Replaced the project authoring page with a StoryPath tree, UUID-addressed
  chapter order, immutable Revision history, and explicit Head review.
- Switched project creation to the replacement Project API so every new project
  receives its root StoryPath. Character names are sent as structured records.
- Removed the fixed 8/13/20 chapter labels. Outline generation accepts the
  requested `chapter_count` from 1 through 500 without mapping it to a pace.
- Added task recovery through persisted Task UUIDs so a page reload can resume
  polling an in-flight authoring command.

The publication controls remain an R6.5 concern. The unused index-based views
and API modules remain until R8.2, when the legacy API is removed as one release
unit.

## Cross-Phase Dependency

The frozen Candidate API consumes an exact checkpoint UUID but does not expose a
checkpoint creation or discovery operation. This UI can restore a checkpoint
from child-path provenance, accept one from route state, or accept an explicit
UUID for the first branch. Repository audit found no production writer that
materializes a new authoring checkpoint for a newly compiled chapter; current
checkpoint rows are seeded by tests or legacy data. R8.5 must prove and, if
necessary, complete that production materialization/discovery path before the
single deployment. The R6.4 browser tests validate the frozen frontend contract
with API fixtures and do not claim that missing backend producer exists.

## Identity And Ordering

- Route state stores `path`, `chapter`, and optional `checkpoint` UUIDs. A
  `display_index` is rendered only as the chapter's position inside one path.
- The path tree is assembled from `StoryPath.parent_path_id`; path selection
  never infers identity from a chapter number.
- Root and child paths can both show chapter position 1 while retaining distinct
  path-chapter UUIDs in navigation and generation requests.
- Archived paths remain readable but all mutation and Head activation controls
  are disabled until the path is restored with its current lock version.

## Revision Review

The workbench lists immutable revisions and requires an explicit Head change for
each artifact family:

| Artifact | Owner identity | Head precondition |
| --- | --- | --- |
| Bible | Project ID | `If-Match` |
| Outline | StoryPath UUID | `If-Match` |
| Chapter | PathChapter UUID | `If-Match` |
| CandidateSet | StoryPath UUID + checkpoint UUID | `If-Match` |
| Script | ChapterRevision UUID | `If-Match` |
| VNGraph | ChapterScriptRevision UUID | `If-Match` |

Generated and manually created revisions are reviewable without automatically
moving Head. Chapter, Script, resources, and VNGraph are loaded from the exact
selected upstream Revision rather than from mutable project-wide state.

## Branch Workflow

- CandidateSet history is loaded for an exact StoryPath checkpoint and displays
  the state snapshot frozen by the selected CandidateSetRevision.
- Repeated generation at the same checkpoint creates another CandidateSet
  revision; it does not create a StoryPath or replace the reviewed Head.
- Only the explicit `Candidate -> StoryPath` action promotes a reviewed option
  into a child path.
- A child path exposes `Same checkpoint branch`. It returns to the parent path,
  restores the original path-chapter and checkpoint UUIDs, and opens the parent
  CandidateSet history. This supports multiple sibling paths from one shared
  prefix without continuing from the first child by mistake.
- StoryPath archive/restore, path-chapter append, and all generation commands
  retain their optimistic-lock or idempotency requirements from the API client.

## Coupling Boundaries

- Project creation establishes the root StoryPath but does not publish it.
- Outline Head supplies the reviewed chapter order; chapter content revisions do
  not mutate that order.
- CandidateSet revisions are retry/version history. StoryPath children represent
  narrative topology, so version creation and branch promotion remain separate
  commands.
- Script generation requires a reviewed ChapterRevision. VNGraph compilation
  requires a reviewed ScriptRevision and renders against immutable resource
  bindings.
- Publication status is displayed only as project context in this checkpoint;
  R6.5 owns readiness, publish, unpublish, and Release history controls.
