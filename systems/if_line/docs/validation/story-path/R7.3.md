## Scope

- Added Alembic revision `0038_backfill_project_publications` after the
  immutable artifact relation backfill.
- Preserved the effective public Release in `ProjectPublication` without
  changing Release manifests or legacy Project publication fields.
- Changed every other `published` Release for the same project to
  `superseded`.
- Recorded every changed status and every created publication pointer so the
  migration has an exact downgrade.

## Active Release Authority

The migration resolves the active Release in this order:

1. an existing `ProjectPublication.active_release_id`;
2. the legacy `ProjectContentHead.published_release_id`; or
3. the project's only non-withdrawn `published` Release.

An exact pointer always wins over Release version ordering. The migration
therefore preserves a lower-version active Release when a newer but inactive
`published` row also exists. It aborts when existing pointers disagree, point
outside the project, point to a withdrawn Release, or when multiple published
Releases exist without an authoritative pointer.

Existing `ProjectPublication` rows retain their pointer, publication time,
lock version, and update time. A missing row is created at lock version 1,
using the selected Release publication time, then the legacy Project
publication time, then the Release creation time as deterministic fallbacks.

## Data Preservation

The migration does not rewrite any of the following:

- `ProjectRelease.manifest_json` or `manifest_hash`;
- `ProjectRelease.published_at` or `withdrawn_at`;
- legacy `Project.visibility`, `is_draft`, or `published_at` fields;
- authoring Heads, StoryPaths, revisions, scripts, or VNGraph artifacts.

`chapter_index` is not read or written by this migration. Release identity is
resolved only through exact Release UUID pointers scoped to `project_id`.

## Reversibility

`_alembic_0038_release_status` stores the previous value of every changed
Release status. `_alembic_0038_created_publication` records only publication
rows created by this migration. Downgrade deletes those created pointers,
restores the exact statuses, and removes both scratch tables. Pre-existing
publication pointers and lock versions are untouched.

The focused test covers:

- a legacy Head selecting a lower-version Release from two published rows;
- a project with exactly one unambiguous published Release;
- a pre-existing target publication at lock version 7;
- unchanged manifest payloads, hashes, timestamps, visibility, and draft
  fields; and
- upgrade, downgrade, and deterministic re-upgrade.
