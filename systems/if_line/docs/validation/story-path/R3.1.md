# R3.1 Validation - Versioned Candidate Set Generation

## Scope

- Added a StoryPath-scoped candidate generation service that freezes the exact
  StoryPath, PathChapter, ChapterRevision, StateSnapshot, checkpoint, Bible,
  Outline, context manifest, provider input, and generation parameters before
  queueing a task.
- Made `Idempotency-Key` the command identity. Reusing one key returns the
  original frozen task even after a Chapter Head moves; different keys can
  generate independent CandidateSetRevisions at the same checkpoint.
- Reused the existing branch task queue and provider adapter behind a versioned
  source envelope. Legacy tasks keep their existing execution path, while the
  worker dispatches target tasks by source schema.
- Persisted one ordered, hashed candidate payload on CandidateSetRevision and
  linked every BranchCandidate to that revision. Versioned revisions and their
  candidate rows reject application-level update and delete operations.
- Kept generated sets review-only. Generation does not create or update a
  CandidateSetHead, BranchEdge, or child StoryPath.
- Added bounded JSON validation for Bible, checkpoint, and state context, and
  revalidates frozen relational ownership, content hashes, request identity,
  provider input, and output count before provider execution or persistence.
- Added migration `0028_candidate_set_payload` with nullable bridge columns for
  legacy CandidateSetRevision rows. New target writers always populate and
  verify `candidates_json` and `content_hash`.
- Froze the historical `0024_candidate_set_versioning` DDL instead of reading
  current ORM metadata, so fresh installs do not receive future columns before
  their owning migration.

## Coupling Audit

- **Context:** generation reads the target PathChapter and its exact immutable
  source IDs. It never discovers story history with `chapter_index` ranges.
- **Head review:** CandidateSetHead is read only to freeze an editorial parent;
  generation never selects its output. CAS activation and query APIs remain
  R3.2.
- **Path creation:** no BranchEdge or StoryPath is written. Candidate promotion,
  shared-prefix creation, and state application remain one R3.3 transaction.
- **Worker:** target and legacy tasks share queue infrastructure and LLM output
  validation, but persistence is selected by the frozen source schema. This
  preserves old queued work until the R8 route cutover.
- **Publication:** generated target candidates remain unreachable from public
  state until reviewed and later frozen into an atomic Release.
- **HTTP:** the target OpenAPI contract exposes CandidateSetRevision
  `content_hash`; target route registration remains R6.2.
- **Migration:** `0028` is additive and nullable for legacy rows. It neither
  backfills nor silently selects a CandidateSet Head; exact legacy relation
  backfill remains R7.2.
