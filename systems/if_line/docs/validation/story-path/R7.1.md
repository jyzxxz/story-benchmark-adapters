# R7.1 Validation - Root StoryPath And Chapter Slot Backfill

## Scope

- Added Alembic revision `0036_backfill_root_story_paths` after
  `0035_script_resource_slot_lock`.
- Creates exactly one active root StoryPath for every legacy project that does
  not already have one. Existing target-created roots are retained.
- Creates an initially empty `StoryPathOutlineHead` when a root does not have
  one, matching the invariant used for newly created projects.
- Converts each legacy root `(project_id, chapter_index)` family into one
  ChapterSlot and one root StoryPathChapter.
- Binds previously unbound ChapterRevisions to the exact root and ChapterSlot.
- Copies the exact legacy ChapterHead Revision UUID, lock version, and update
  time into the root PathChapter Head.

## Ordering And Identity

The legacy chapter family set is the union of unbound/root ChapterRevisions,
legacy ChapterHeads, unbound/root OutlineRevision rows, and any remaining
legacy `chapter_outlines` or `chapter_contents` rows. Child StoryPath artifacts
are explicitly excluded even though they retain a presentation index.

Root, Slot, and PathChapter IDs use UUIDv5 identities derived from the legacy
project and chapter family. Re-running after a downgrade therefore produces
the same IDs. PathChapters are sorted by the legacy positive index and linked
through a complete predecessor chain; gaps in presentation order do not break
the chain.

`chapter_index` is used only inside this one-time migration as a bridge from
the legacy family key. Runtime authoring and public readers continue to use
StoryPath, PathChapter, Slot, and Revision UUIDs.

## Conflict Policy

The migration aborts instead of guessing when it encounters:

- more than one root StoryPath for a project;
- multiple root ChapterSlots for one legacy family;
- a Slot owned by another project or StoryPath;
- a partially populated ChapterRevision path binding;
- conflicting legacy and PathChapter Head pointers; or
- a legacy Head whose Revision is outside the expected root Slot.

This keeps malformed or mixed data from being silently merged. A partial
historical repair database that has no `projects` table is left unchanged so
the existing `0035` repair migration remains independently usable.

## Reversibility

Three `_alembic_0036_*` scratch tables record only rows created or fields
changed by this migration. Downgrade restores existing PathChapter state and
ChapterRevision bindings, removes created placements and Slots, removes only
the new empty Outline Heads and roots, and then drops the scratch tables.

The roundtrip test verifies:

- exact Head Revision IDs and lock versions;
- one Slot shared by every Revision in a legacy chapter family;
- complete predecessor ordering across outline-only and prose chapters;
- preservation of an existing root and Outline Head;
- cleanup back to `0035`; and
- stable IDs after a second upgrade to head.
